# Stage 3 S3.4 owner-proof kernel and minting evidence

- Integrated baseline: `outcome-loop` `e48aafea703097846c39ab7e16afb7f626626f31`
- Parked kernel WIP: `5f855c9bd84f84cedbf3c6804f8a11aab5583861`
- Candidate scope: owner-proof kernel, durable store, and authenticated routine-proof minting only

Implemented:

- caller-only random owner-proof bearer with only a SHA-256 verifier persisted;
- exact binding to the authenticated startup app run, mission, content digest, typed versioned target digest, closed command class, expiry, and material confirmation reference;
- routine classes `turn|steer|answer|interrupt|cancel` without a material confirmation reference;
- material classes `replace|approval|accept` represented by the kernel but rejected by the HTTP minting route until a daemon-native confirmation seam exists;
- atomic one-time verification/consumption, exact mint replay without bearer re-return, and constant-time tuple checks;
- typed SQLite record, store, migration 0147, generated sqlc output, migration ledger and rollback proof;
- one closed mapping to the S3.1 transport class vocabulary. Mapping does not authenticate either side or grant authority;
- loopback-only `/internal/owner-commands/owner-proofs`, authenticated with the existing `KennelOwner` authority;
- app-run identity taken only from the authority's typed authentication result. The request cannot supply app-run identity, confirmation references, expiry, proof ID, or bearer/verifier fields;
- daemon-fixed two-minute proof expiry and generated proof ID;
- route absent without both owner authority and proof kernel, and hidden from LAN/rebinding hosts.

Narrowed boundary:

This candidate does not add a post-pair adapter command RPC, alter the frozen S3.3 pairing server, create governed command claims, or claim crash-after-consume reconciliation. It does not mint material proof classes because no daemon-native confirmation validator is yet wired. Those seams are specified separately in `docs/handoffs/2026-09-17-stage-3-post-pair-command-ingress-design.md` and require review before code.

The frozen S3.3 invariants remain unchanged: pairing intent replacement is atomic, only the prove/consume winner writes terminal pairing evidence, and `Coordinator.Issue` remains reachable only through the authenticated owner pairing-intent route.


## Formal target amendment

The post-pair ingress implementation found that the original `targetId + int64 targetGeneration` could not losslessly bind existing string controller/revision/turn/question fences. Migration 0148 replaces it with the digest of a closed, versioned typed target payload. This preserves exact tuple binding without parsing, hashing-to-fit, or dropped fields. Existing short-lived proofs are invalidated on upgrade. See `docs/handoffs/2026-09-17-stage-3-post-pair-command-ingress-implementation.md`.
