## Self-review pass

Before finalizing this package, an independent review of the transcript (not a rerun of the
plan, a fresh read of the actual code and tests) surfaced two real defects, both fixed and
covered by new tests before this handback:

1. **Durable-audit poisoning.** `recordResultBestEffort` was called on every failed proof,
   including a rejected attempt against a challenge that was still `pending` (wrong tuple,
   wrong secret, undeclared class, or an unswept expiry). A single bad guess by an attacker
   could permanently set `result_code='tuple_mismatch'` on a challenge the legitimate holder
   then went on to pair successfully — because `RecordHarnessPairingResult`'s `WHERE
   result_code IS NULL` guard means the *first* write wins, and the eventual success write is
   silently swallowed. Fixed: a failure is now recorded only when the challenge was already
   terminal (`consumed`/`superseded`) at read time; a rejected attempt against a still-`pending`
   row records nothing, since the challenge's lifecycle isn't over. Covered by a new assertion
   in `TestProve_AdversarialTupleMatrix`: after a bad attempt followed by a legitimate proof, the
   durable `ResultCode` reads back `succeeded`, not the earlier failure code.
2. **Missing generation check.** Binary acceptance criterion 4 requires that changing the
   challenge generation fails proof, and invariant 3 lists generation as part of the bound
   tuple, but `ProveRequest`/`wireProve` did not carry it and `compareTuple` did not check it —
   the criterion was vacuously satisfied rather than enforced. Fixed: `ExpectedGeneration` is
   now part of the proof tuple end to end (coordinator, wire protocol, client), compared with
   the same `binary.BigEndian`-then-`subtle.ConstantTimeCompare` idiom
   `harnessconnection.Kernel.Authenticate` uses for its own generation check. Covered by a new
   `wrong_generation` case in the adversarial matrix.

All test commands and counts below reflect the code *after* these two fixes.

## What this closes

A Codex-first adapter can prove possession of one fresh, daemon-issued challenge over a
protected user-local Unix-domain socket and receive one caller-only S3.1 transport bearer.
Replayed, stale, substituted, or wrongly-bound proofs fail closed with a single generic wire
response, never disclosing which tuple field or proof byte was wrong, and never touching the
frozen S3.1 kernel's Issue/Authenticate/Rotate/Revoke surfaces themselves.

### One resolved gap in the frozen surface, not a change to it

`Kernel.Issue` converges silently on an exact retry: if a connection with the same ID and
tuple already exists, it returns `IssuedConnection{Connection: ..., Bearer: ""}` — success,
but no bearer (`kernel.go:69-74`). A `pair` challenge that reaches this path has already been
consumed (single-use) and cannot be retried, so a caller who received `Bearer == ""` here would
otherwise be stuck with no way to ever obtain a bearer for a challenge it legitimately proved.

**Resolution (in `harnesspairing.Coordinator.Prove`, not in the kernel):** an empty bearer
after a successful kernel call is treated as a fail-closed result
(`domain.HarnessPairingResultBearerUnavailable`), not a success. The caller must request a new
challenge. This never triggers in the intended flow, where each pairing challenge targets a
connection ID freshly chosen by the trusted issuing caller, because the coordinator's own
`Issue` supersedes any prior pending challenge for that connection ID before minting a new one.
It is now exercised directly by `TestProve_BearerUnavailableWhenConnectionAlreadyExists`
(pre-create the connection via the kernel directly, then prove a pairing challenge that targets
the exact same ID/tuple: asserts `BearerUnavailable`, no bearer, and that the challenge is
burned — a retry gets `Replayed`, not another attempt at the kernel). If the builder wants this
to be an S3.1 kernel-level distinction instead (e.g. a typed conflict return from `Issue`), that
is the one semantic decision this package could not resolve on its own frozen-surface
authority, and is flagged here rather than patched into `kernel.go`.

A second edge case was identified and is handled: two `pair` challenges for different
connection IDs but an identical binding tuple collide on `harness_connections`' unique index at
generation 1. `InsertHarnessConnection`'s `ON CONFLICT DO NOTHING` makes the second insert
affect zero rows, and the existing `CreateHarnessConnection` store method then looks up the
*inserted* ID (not the ID that actually holds the conflicting row), gets `sql.ErrNoRows`, and
returns a real Go error — not one of the three closed sentinel errors. The coordinator's `Prove`
treats any non-nil, non-sentinel error from `issueOrRotate` as
`domain.HarnessPairingResultInternalError` and fails closed; it never panics or leaks the
conflicting row's identity. Now exercised directly by
`TestProve_UniqueIndexCollisionOnDifferentConnectionIDFailsClosed`.

## Protocol transcript (redacted)

Two RPCs, each served by a fresh connection to the protected socket (no session affinity):

```
--> {"type":"request_challenge","kind":"pair","connection_id":"hc-1",
     "installation_id":"...","adapter_digest":"<sha256-hex>","harness_identity":"codex",
     "provider_version":"0.154.0","protocol_fingerprint":"<sha256-hex>",
     "mission_id":"...","app_run_id":"...","capability_classes":["turn"],
     "expected_generation":1}
<-- {"ok":true,"challenge_id":"<hex>","secret":"[REDACTED-32-BYTES-HEX]"}

--> {"type":"prove","challenge_id":"<hex>","secret":"[REDACTED]",
     "installation_id":"...","adapter_digest":"<sha256-hex>","harness_identity":"codex",
     "provider_version":"0.154.0","protocol_fingerprint":"<sha256-hex>",
     "mission_id":"...","app_run_id":"...","capability_classes":["turn"],
     "expected_generation":1}
<-- {"ok":true,"bearer":"[REDACTED-32-BYTES-HEX]"}

-- every failure, whatever the cause --
<-- {"ok":false}
```

`{"ok":false}\n` is a single package-level byte slice (`genericFailure` in `protocol.go`),
written from exactly one call site (`Server.writeFailure`). It is what
`TestServer_EveryFailureReasonProducesIdenticalWireBytes` asserts byte-for-byte across
malformed JSON, an unknown message type, an unknown challenge ID, a replayed challenge, a wrong
secret, and a wrong tuple field.

### Cryptographic construction

- Challenge ID: 16 random bytes, hex-encoded. Not secret; safe to log.
- Challenge secret: 32 random bytes, hex-encoded. Caller-only; returned exactly once by
  `request_challenge`, never again.
- Challenge verifier (durable): `hex(sha256(secret))`. Stored in
  `harness_pairing_challenges.proof_verifier`; the raw secret is never persisted.
- Proof comparison (`compareTuple` in `coordinator.go`): every bound field — the verifier hash,
  installation ID, adapter digest, harness identity, provider version, protocol fingerprint,
  mission ID, app run ID, the challenge generation, and the normalized capability-class set — is
  compared in constant time and AND-reduced into one `valid` bit. String fields are SHA-256-hashed
  then compared with `crypto/subtle.ConstantTimeCompare`; the generation is compared with
  `encoding/binary.BigEndian`-encoded 8-byte buffers through the same `ConstantTimeCompare`. This
  is the exact idiom `harnessconnection.Kernel.Authenticate` already uses
  (`equalString`/`equalGeneration` in `kernel.go`), reused rather than reimplemented.
- S3.1 bearer: minted by the frozen kernel itself (`newBearer` in `kernel.go`), untouched by
  this package.

### Binding tuple (invariant 3)

Connection ID, installation ID, adapter digest, harness identity, provider version, protocol
fingerprint, mission ID, app run ID, the requested capability-class set, and — via
`expected_generation` — the challenge generation, are all captured in the durable challenge row
at issue time by the trusted caller and re-verified in full at proof time. The adapter selects
none of them; it only echoes back what it independently knows about itself.

### Pre-existing failure, not a regression

`go test ./internal/harnessconnection/... -race` fails `TestConcurrentRotationHasOneWinner`
with a genuine data race: two goroutines share one `bytes.Reader` as the kernel's random
source (`kernel_test.go:88-90`), and `bytes.Reader.Read` mutates its own read cursor without
synchronization. **This file was not touched by this slice** (file ownership forbids editing
`kernel.go`/`kernel_test.go`), and the race is reproduced identically by checking out the pristine
baseline commit `c19331d7ad8e7abb9b4bf3166c2c27e29bfca29a` into a separate worktree and running
the same command with no other changes present. Without `-race`, the same test passes
deterministically (it happens to work by luck of scheduling). This is a pre-existing S3.1 test
defect, unrelated to this package, and is reported here rather than fixed because
`kernel_test.go` is outside this slice's file ownership.

## Secret-scan evidence

`TestBoundedNativeMacOSTransportProof` (native, this run, on Darwin arm64):

1. Generates a known canary secret and bearer via two independent deterministic byte sources
   (`COORDINATOR-SECRET-CANARY-...` and `KERNEL-BEARER-CANARY-...`), so the exact values are
   known ahead of time rather than intercepted from internals.
2. Runs a full pair → prove → bearer → authenticate → restart flow over the real protected
   Unix socket.
3. Scans, byte-for-byte, for the raw canary secret and the raw canary bearer in:
   - the real on-disk SQLite file (`os.ReadFile` of `kennel.db`)
   - the server's captured `slog` output
   - a `ps -A -o command` snapshot taken during the run
   - the current process's environment (`os.Environ()`)
4. **Zero matches** in all four surfaces.
5. Sanity check: confirms the DB file *does* contain each value's SHA-256 hex verifier — the
   one-way form the contract permits — so the zero-match result above is not a false negative
   from scanning an empty or irrelevant surface.

Argv is not included as a scanned surface because no `os/exec` invocation anywhere in this
package's code passes the secret or bearer as an argument — verified by inspection: the only
process spawned by the runner (`ps`) carries no pairing data, and the client/server exchange is
entirely in-process Go calls plus a Unix-socket byte stream. There is no separate adapter
process in this slice's scope to place a value in argv in the first place.

The repository worktree itself was also grepped for both canary seed strings; the only match is
the seed-constant literal in `native_proof_test.go` that *generates* the canaries, not a leaked
runtime value (confirmed by excluding that file and finding zero remaining matches).

## Unresolved decisions / blockers for the builder

1. **`Kernel.Issue`'s empty-bearer convergence path** (see "One resolved gap" above) — resolved
   at the S3.3 layer by treating it as fail-closed, and now covered by
   `TestProve_BearerUnavailableWhenConnectionAlreadyExists`. Flagging in case the builder
   prefers a typed distinction at the S3.1 kernel level instead; no `kernel.go` change was made
   here.
2. **sqlc regeneration** — the hand-written generated file should be diffed against real sqlc
   v1.31.1+ output once a toolchain that can build it is available; see the "Files" section for
   exact reproduction of the install failure.
3. **Wrong-peer rejection** was not exercised natively (single-uid environment); it is
   unit-tested with an injected fake verifier only. A genuine cross-uid proof requires a
   multi-user CI runner or a container with a second user.
4. **Daemon/controller wiring is explicitly out of this slice's scope.** `Coordinator.Issue` is
   designed to be called by an already-authenticated internal caller (the S1 owner path); no
   such caller exists yet in this slice. The transport server currently honors any
   `request_challenge` from a peer that passes the local identity check — because deciding
   *which* connection IDs are eligible to receive a challenge right now (a "pairing mode" or
   intent window opened by the owner) is a daemon-integration decision, not built here. This
   should be the first thing the follow-on allowlist covers.
