# Stage 2 S2.2: truthful turn-send acceptance

Date: 2026-09-16
Branch: `instinct/stage2-s2.2`

## Boundary implemented

Governed Chat turn delivery now reuses the existing Chat controller and conversation timeline. It does not add a session engine or provider event framework.

Before provider contact, the controller records one durable command claim, freezes the Plan revision and negotiated Chat capability fingerprint, and compare-and-set advances the claim to `dispatching`. The Codex adapter returns content-free transport evidence and one of four provider-neutral classifications:

- `not_sent`: no complete request frame crossed the transport;
- `rejected`: the provider explicitly rejected a completely written request;
- `delivery_unknown`: a complete frame was written but acceptance cannot be proven;
- `acknowledged`: the provider returned a turn ID.

The governed command row records acknowledged/rejected/unknown. The existing conversation turn remains the visible timeline. An unknown turn remains nonterminal and blocks later provider effects. Exact replay returns the existing command state and never contacts the provider again.

On restart, ordinary orphan settlement excludes governed claimed, dispatching and unknown turns. Stable native history may reconcile an unknown command to acknowledged when the replay supplies the same provider conversation, client message ID and provider turn ID under the same Plan and capability fences. Absence from history does not prove rejection, so it remains unknown. A crash-left `dispatching` claim becomes unknown rather than being redelivered.

## Falsifiers exercised

Focused real-SQLite controller tests establish:

- dispatching is durable before provider contact;
- provider acknowledgment binds the existing turn and command to the returned provider turn ID;
- explicit rejection is not unknown;
- complete-write timeout becomes durable `delivery_unknown`;
- exact replay after unknown does not contact the provider twice;
- later work does not cross the provider seam while unknown is unresolved;
- orphan settlement does not falsely fail unknown;
- restart reconciles matching stable native history without redispatch.

The controller, store, ports and Codex adapter packages pass, including repeated race runs and vet. A repository-wide `go test ./...` exceeded the 120-second command window, so no repository-wide green claim is made here.

## Industry comparison

This boundary follows the same core rule used by major public APIs: a caller-generated key identifies one semantic request, retries with the same request do not repeat the effect, and changed parameters under the same key conflict.

- Stripe persists the first result for an idempotency key and rejects reuse when parameters differ. It also distinguishes failures before endpoint execution, which remain retryable, from requests whose execution began. https://docs.stripe.com/api/idempotent_requests
- Amazon EC2 client tokens return the original successful result for the same token and parameters without another action, and return `IdempotentParameterMismatch` when parameters differ. https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html
- Google Compute Engine request IDs let a retry after timeout be recognized and ignored when the original request was already received, preventing duplicate commitments. https://docs.cloud.google.com/compute/docs/reference/rest/v1/instances/insert
- Google Cloud retry guidance says only idempotent or conditionally idempotent operations should be retried by default; a transient transport status alone is not enough. https://docs.cloud.google.com/storage/docs/retry-strategy

Kennel is deliberately more conservative where the provider does not offer a durable idempotency result: a fully written request with no acceptance proof becomes visible `delivery_unknown` and is not retried. This is not described as exactly-once delivery.

## Remaining S2.2 limits

- History can currently prove acknowledged delivery, not a historical explicit rejection.
- Providers without stable replay cannot clear unknown automatically.
- The next review should probe crash points around timeline append and command state transition together, and should verify how an operator-visible unknown is cleared or escalated without unsafe redelivery.
