# Stage 3 S3.5 reconnect evaluator evidence

- Baseline: `outcome-loop` at `c65051bce745ba05587446da259a2cb19b700f92`
- Design: `docs/handoffs/2026-09-17-stage-3-s3.5-reconnect-evaluator-freeze.md`
- Scope: pure reconnect evaluation and typed reader seams; no UI or daemon startup wiring

## Implemented boundary

- Typed daemon readiness, durable mission existence, pinned mission profile, retained delivery block and authenticated pairing observation contracts.
- Evaluation attaches before any launch decision, requires an explicit compatible daemon identity/readiness generation, selects the exact requested durable mission, then loads its pinned profile. Mission existence and profile presence are separate facts, so an existing mission with no profile is not mislabeled missing.
- Daemon and pairing observations must be fresh and cannot come from the future. PID/socket existence alone is not a readiness fact.
- `delivery_unknown` has higher precedence than adapter pairing/compatibility. Its only projected repair is `review_delivery_evidence`; reconnect never retries or settles a command.
- Fresh S3.3 pairing facts are an explicit required seam. `UnavailableHarnessPairingFacts` returns `ErrHarnessPairingFactsUnavailable`; evaluation projects `action_needed / pairing_facts_unavailable / pair_adapter`. Discovery or process state is never substituted.
- Existing S3.1 `EvaluateHarnessConnection` remains the sole adapter state classifier. S3.5 first verifies the durable pinned profile, current app run, provider version, installation/digest/protocol and generation, then delegates connected/degraded/action-needed classification to S3.1.
- Result exposes one state, one primary reason and one repair action. It reads only; it cannot create a mission, restart a daemon, rotate credentials, migrate a profile or replay work.

## Local evidence

Focused normal and race tests cover connected, daemon-unreachable, missing mission, retained delivery-unknown precedence, missing S3.3 facts, stale observation and cancellation, plus adjacent S3.1/S3.2 packages.

## Explicitly unclaimed

- No daemon launch lease or Electron attach wiring.
- No persistence schema for mission profile or readiness evidence; the reader ports must be backed by the existing mission model during integration.
- No S3.3 pairing facts implementation.
- No UI projection or operator evidence mutation route.
- No Mac desktop quit/reopen proof.
