# September 18 integration milestone

> **Classification (2026-09-15):** Historical launch roadmap; not the current implementation order. Use the [canonical documentation map](../README.md).


September 18 is a forcing function for integration and review, not Kennel's product definition. [ROADMAP.md](../../ROADMAP.md) is the quality-gated canonical roadmap. This view shows the dependency-ordered work intended to make the complete core loop reviewable around that date. A slice does not pass because the date arrived. The detailed what, why, invariants, implementation sequence, failure matrix, evidence, and rollback plan is in the [W1 implementation plan](w1-implementation-plan.md).

## Locked clean-profile cut (2026-09-17)

The dependency order is: install/start -> add or import a project (an empty project is valid) -> pair Codex inside that project and its stable mission -> create the Outcome -> freeze one truthful Contract and Plan -> authorize separately from Start -> run one persistent steerable session with durable proof. Pairing is never platform-global. On desktop/daemon restart, a new app run rotates/re-pairs a new connection generation without rewriting mission lineage; the prior generation remains durable evidence but cannot authorize commands for the new app run.

## Readiness test

A serious harness power user should find Kennel's planning, orchestration, visibility, recovery, proof, and UI materially better than manually operating native sessions. Only packaged-proven behavior may be presented as working.

The milestone requires the complete Codex-first Ask -> Approve -> Watch -> Decide loop, including Verification, Result review, bounded rework, and explicit owner Accept. Watch and Decide are not optional polish.

## Current baseline

At `beta` commit `5304d569aa2e29f0cc77d57539aa2f65a4d01484` on 2026-09-14:

- the repository contains durable Outcome, immutable Contract and Plan revision, WorkUnit, Attempt, authorization, evidence, Verification, Result, rework, and Accept concepts;
- serial WorkUnit execution and governed repository tools exist;
- provider verification, approval-time admissibility, semantic WorkUnit coherence, recovery lineage, and mission projection are not yet one proven path;
- the complete packaged macOS Outcome journey to owner Accept is not proven;
- U2.1 Ask/Approve interaction work remains a separate review package and must be wired to truthful admission semantics before its approval rail is considered complete.

See [docs/STATUS.md](../STATUS.md) for the evidence ledger. Status in this file is planning status, not a shipped claim.

## Required evidence for every slice

- exact baseline SHA and changed files;
- root-cause statement and smallest correct change;
- focused regression proof plus adjacent contract gates;
- full relevant gates, with pre-existing failures separated;
- generated-code and migration checks when applicable;
- visual inspection of real rendered states for UI work;
- packaged/native evidence for packaged/native claims;
- explicit list of what was not tested or claimed;
- documentation status updated in the same reviewed package.

## Do not cut for the date

- authority and trust-boundary validation;
- feasibility before approval;
- complete Result, Verification, rework, and Accept;
- truthful recovery and restart behavior;
- strong Watch and Decide UX;
- accessibility and reduced motion;
- evidence quality or packaged proof.

If these do not pass, the milestone is not ready. Narrowing the demonstration repository or number of providers is acceptable; weakening the loop is not.

## Deferred by dependency, not date pressure

| Extension | Dependency before it is useful and safe |
| --- | --- |
| Claude Code, OpenCode, and Pi execution parity | Codex completes the loop; adapter conformance and native session semantics are stable |
| Parallel WorkUnit execution | scheduler projection, leases, fences, recovery, and consolidation pass serial failure tests |
| Portable cross-harness memory | Result capsule and Context Packet contracts are stable, source-linked, correctable, and authority-neutral |
| Teams and shared policy | single-owner authority, audit, acceptance, and erasure semantics are proven |
| Linux completeness | platform sandbox and packaged enforcement can make the same claims as macOS |
| Broad motion and visual polish | all motion is attached to reachable lifecycle state and passes performance/accessibility review |
| Schema and compatibility cleanup | canonical callers are redirected, old records are migrated, and rollback/history needs are proven |
| Broad module/organization rename | product and migration work no longer compete for the same risk budget |

## Safe removal order

For every legacy path: enumerate callers, identify persisted records and migrations, redirect to the canonical path, prove focused and full gates, then delete in a small reviewable change. Hide obsolete UI before deleting history. "Looks legacy" is not evidence.
