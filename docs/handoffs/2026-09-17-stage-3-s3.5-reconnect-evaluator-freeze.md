# Stage 3 S3.5 reconnect and connection evaluator design freeze

- Baseline: `outcome-loop` at `c65051bce745ba05587446da259a2cb19b700f92`
- Depends on: S3.0 contract, S3.1 connection kernel, S3.2 discovery/manifest, reviewed S3.3 local pairing transport
- Scope: contract only; no production code
- Status: design frozen for implementation review

## Outcome

When the desktop opens or returns, it attaches to the already-running Kennel daemon, resolves the durable mission the window is meant to show, evaluates the pinned harness profile against fresh adapter facts, and exposes exactly one truthful state plus one repair action. It never restarts a healthy daemon, forks a mission, rotates credentials merely because the desktop restarted, or converts delivery uncertainty into success/failure.

## Terms

- **Desktop run:** one renderer/main-process lifetime. It is disposable and is not mission identity.
- **Daemon instance:** the running Kennel backend, identified by a daemon instance ID and readiness generation supplied by the daemon.
- **Mission:** the existing durable mission lineage identified by `mission_id`. Desktop reconnect selects; it does not create or rewrite it.
- **Pinned profile:** the mission's admitted harness kind, installation identity, adapter digest, provider version/protocol fingerprint, required/optional classes and connection generation. It changes only by a new Attempt or an explicit reconnect migration that passes the same authority gates as the original profile decision.
- **Observation:** fresh daemon/discovery/pairing facts with timestamps and provenance. It is evidence, not desired state.
- **Connection evaluation:** deterministic projection from pinned profile + durable connection + fresh observation + retained delivery blockers.

## Reconnect sequence

1. **Attach before launch.** Desktop attempts the protected local daemon endpoint. It starts a daemon only when no endpoint exists and the launch lease proves no other owner is starting one. A connection error alone does not authorize killing or replacing a process.
2. **Prove readiness and identity.** The daemon returns its instance ID, readiness generation, schema/API compatibility and server time over the protected channel. PID, process existence and an open socket are insufficient.
3. **Select the durable mission.** The desktop supplies its last durable `mission_id` reference. The daemon resolves that exact mission. Missing/invalid identity enters action-needed; it never chooses the newest mission or creates one silently.
4. **Load the pinned profile.** Read the mission's existing profile/binding. A desktop preference or currently discovered default cannot overwrite it.
5. **Observe current facts.** Discover the canonical installation and protocol, then consume the S3.3 authenticated adapter transport facts. Bound each observation to daemon instance, mission, app run and generation. Stale cached observations cannot produce `connected`.
6. **Evaluate once.** A pure evaluator returns one public state, one stable reason, one repair action and internal evidence references.
7. **Resume projection.** Rehydrate the existing mission/Attempt/turn state. Do not submit or replay work as part of reconnect.
8. **Reconcile blockers separately.** `delivery_unknown` remains blocked until positive provider evidence is attached. Adapter liveness does not settle it.

## Public state contract

| State | Meaning | Repair |
| --- | --- | --- |
| `connected` | Exact durable mission/profile and current authenticated adapter generation match fresh verified facts; all required classes exist | none |
| `degraded` | Identity/authentication/current generation are valid, all required classes exist, but an optional class is missing | `review_degraded_capability` |
| `action_needed` | Attach, mission selection, pairing, generation, binding, required compatibility or retained operator evidence is not safe enough to continue | exactly one stable action below |

No fourth “connecting,” “offline,” or “unknown” terminal state is added. UI may show a bounded in-progress affordance while facts are being gathered; timeout settles to `action_needed`, never to a guessed offline state.

## Stable reasons and precedence

The first matching row wins so callers cannot choose a friendlier reason:

| Precedence | Reason | Repair action |
| --- | --- | --- |
| 1 | `daemon_unreachable` | `start_or_repair_daemon` |
| 2 | `daemon_identity_mismatch` | `repair_daemon_endpoint` |
| 3 | `mission_not_found` | `choose_existing_mission` |
| 4 | `mission_profile_missing` | `repair_mission_profile` |
| 5 | `delivery_unknown` | `review_delivery_evidence` |
| 6 | `unpaired` | `pair_adapter` |
| 7 | `revoked` or `binding_mismatch` | `repair_pairing` |
| 8 | `expired` | `rotate_capability` |
| 9 | `stale_generation` | `reconnect_adapter` |
| 10 | `protocol_drift` or `required_capability_missing` | `repair_compatibility` |
| 11 | `optional_capability_missing` | `review_degraded_capability` |

Rows 6-11 preserve the S3.0/S3.1 vocabulary. S3.5 must not reinterpret those reasons. If multiple failures exist, the evidence retains all facts, but only the highest-precedence repair is presented.

## Pinned profile semantics

1. Mission ID is durable; app-run ID and desktop run are not substitutes.
2. A reconnect with the same profile may bind a new desktop/app run through the reviewed S3.3 rotation path. It must not mutate mission lineage.
3. A newly installed adapter version does not automatically move an active mission.
4. If the old pinned adapter generation remains runnable, reconnect uses it. If it is unavailable or unsafe, evaluation returns `action_needed` and proposes explicit profile migration.
5. Profile migration records old/new profile fingerprints, reason, authority evidence, connection generation and rollback target. It never occurs mid-turn.
6. Optional capability drift may remain degraded only when all required classes and original authority boundaries remain intact.

## Blocked-unknown operator route

S3.5 consumes the S3.0 contract rather than adding retry semantics. The route shows retained command ID/class, correlation references, dispatch generation, timestamps and available reconciliation evidence. Its only decisions are:

- attach positive acknowledgement evidence and reconcile;
- attach positive rejection/no-effect evidence and reconcile;
- keep blocked when evidence is insufficient.

Reconnect time, empty provider history, successful adapter pairing, operator preference and process restart are not positive no-effect evidence. No “retry anyway” action exists.

## Persistence boundary

Prefer references on the existing mission/profile records plus evaluator evidence, not a new Session engine. Persist only what survives restart: mission/profile fingerprint, daemon/connection generations, observation timestamp/provenance, evaluation reason/action and evidence references. Do not persist renderer state, transient progress, bearer material or a duplicate conversation timeline.

## Falsifiers

- Closing and reopening desktop creates a new mission or restarts a healthy daemon.
- An open socket or PID yields `connected` before readiness identity and adapter authentication.
- Reconnect silently selects the latest mission, adapter or profile.
- Credential rotation rewrites mission lineage.
- Two simultaneous desktops produce two active connection generations.
- An adapter update changes an active mission mid-turn.
- `delivery_unknown` becomes failed, successful or retryable without positive evidence.
- Two public repair actions are shown for one evaluation.
- Restart turns stale cached facts into `connected`.

## Implementation ownership proposal

After S3.3 review, allow only a small evaluator domain/service, the existing daemon attach/start seam, existing mission/profile reads, narrow DTO/UI projection, and focused persistence/tests. Do not add a generic reconnect framework, second controller, new provider abstraction, installer code or S3.3 cryptography in this slice.

## Gate matrix

- attach to healthy daemon without restart;
- no-daemon single-winner launch race;
- wrong/stale endpoint identity;
- exact mission resume after desktop restart;
- missing mission fails without silent creation;
- pinned profile preserved across newly discovered adapter version;
- S3.1 reason/repair parity tests;
- stale/expired/revoked/concurrent-generation cases;
- optional vs required capability drift;
- retained `delivery_unknown` across daemon and desktop restart;
- operator positive-ack, positive-no-effect and insufficient-evidence paths;
- focused race tests and packaged macOS reconnect evidence.

S3.5 closes only when the packaged macOS run proves that quitting/reopening the desktop attaches to the same daemon and mission, preserves pinned profile/lineage, exposes the expected one state/action, and does not replay work.
