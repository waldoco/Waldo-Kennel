# Worker slice handoff: S3.3 pairing challenge and thin adapter transport

## Slice

- **Milestone / slice:** Stage 3 / S3.3
- **Worker:** Claude, implementation and bounded native transport evidence
- **Builder/semantic owner:** Instinct matrix builder
- **Baseline branch and SHA:** `instinct/stage3-s3.1` at `c19331d7ad8e7abb9b4bf3166c2c27e29bfca29a`
- **Depends on:** S3.0 frozen contract and S3.1 identity/capability kernel; consume the S3.2 manifest identity only after the builder freezes and supplies that exact shape
- **Blocks:** S3.5 reconnect/evaluator integration and S3.6 integrated native proof
- **Status:** not started

## Outcome

A Codex-first adapter can prove possession of one fresh, daemon-issued challenge over a protected user-local channel and receive one caller-only, least-privilege S3.1 transport bearer; replayed, stale, substituted or wrongly bound peers fail closed without disclosing a secret or gaining owner authority.

## Root cause

Protocol negotiation and plugin presence identify neither the adapter process nor the exact installation/build/app-run/mission generation carrying a command. Without a one-time possession proof at the local transport boundary, an unpaired, replaying or substituted adapter could reach transport operations or retain a stale bearer.

## Invariants

1. Pairing authenticates adapter transport only. Adapter content is never owner content or owner authority.
2. The daemon creates the random challenge and bearer. The adapter cannot select identity, capability classes, generation, expiry or verifier.
3. A challenge is single-use, short-lived and bound to connection ID, installation identity, adapter digest, harness identity, provider/protocol fingerprint, mission, app run, requested classes and challenge generation.
4. Proof comparison is constant-time. Failure responses do not reveal which tuple field or proof byte failed.
5. Durable state may retain only one-way challenge/bearer verifiers and non-secret evidence. Raw challenges and bearers never enter the database, argv, environment, prompts, renderer JavaScript, repository files, logs, errors, telemetry, plugin-managed storage or exported JSON/string shapes.
6. The S3.1 bearer is returned only on the successful local response to the caller that proved possession. Exact retries converge without returning or minting another bearer.
7. Crash/restart never guesses success, silently reissues, resurrects a consumed/stale challenge, or marks a connection connected.
8. Concurrent pair/rotate calls have one durable winner. Old/stolen/stale credentials cannot become valid again.
9. The transport proposes and carries data only. It adds no owner-proof command, confirmation bypass, policy interpretation, filesystem/network grant or Result Acceptance path.
10. Unknown or incomplete state fails closed with retained non-secret evidence for the builder's later evaluator/operator route.

## In scope

- One daemon-owned, one-time pairing-challenge record and lifecycle: issue, prove/consume, expire and invalidate on superseding generation.
- Protected user-local transport with explicit peer/endpoint possession checks using an existing local IPC primitive where possible.
- A thin adapter client that requests a challenge, submits possession proof and receives the S3.1 caller-only bearer.
- Wiring only from a successful proof into the frozen S3.1 kernel issue/rotate API.
- Narrow non-secret audit evidence: connection/challenge IDs, timestamps, generation, result code and tuple fingerprints already safe to retain.
- Deterministic Linux contract/adversarial tests and a bounded real macOS local-transport runner/evidence package.

## Binary acceptance criteria

1. A fresh challenge plus exact possession proof and exact tuple creates/rotates exactly one S3.1 connection generation and returns one bearer only to that local caller.
2. Replaying a consumed proof returns a generic failure, creates no generation and returns no bearer.
3. A stolen challenge without the possession secret fails; a stale/expired/superseded challenge fails.
4. Changing any connection ID, installation ID, adapter digest, harness identity, provider version, protocol fingerprint, mission, app run, generation or requested class fails.
5. Requesting an undeclared class or a class outside the frozen closed set fails before S3.1 issuance.
6. Crash before durable challenge creation leaves no usable challenge. Crash after creation but before return leaves only a durable verifier/evidence and requires a new challenge. Crash after proof consumption but before bearer delivery does not replay or mint a second bearer; state is explicitly non-success/repair-required.
7. Two concurrent proofs/pairs have exactly one winner. Two concurrent rotations have exactly one current generation; the loser and all prior bearers fail authentication.
8. Restart preserves only the safe verifier/lifecycle state and never persists/reconstructs a raw challenge or bearer.
9. Transport refuses non-local/unprotected endpoints and peers that fail the platform identity/permission check; no fallback listener starts.
10. Searches of persisted DB rows, process argv/environment, captured stdout/stderr/logs, telemetry, renderer bundles, repo worktree and plugin storage find no raw challenge or bearer.
11. Adapter-originated payloads cannot invoke an owner-authorized command or widen capabilities without the separate S3.4 owner proof. S3.3 exposes no such API.
12. Migration upgrade/rollback, focused normal tests, focused race tests and adjacent S3.1 regression tests pass.
