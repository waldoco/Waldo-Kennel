# S3.4 integration requirements after S3.3

Baseline kernel WIP: `instinct/stage3-s3.4-wip` at `7d930d386e9fbe9d73d261f023698eeb2fb1b528` before this note. S3.3 must land first and freeze its paired-adapter authentication result and protected local ingress.

## Required separation

Every adapter-carried owner command records and verifies two independent facts:

1. **Adapter transport authentication:** the accepted S3.3 ingress supplies the S3.1 `HarnessConnectionID`, generation, exact binding fingerprint and authenticated transport class. This proves only which paired transport carried the request.
2. **Owner proof:** `ownerproof.Kernel.VerifyAndConsume` verifies the separate proof against app run, mission, exact content digest, target ID, target/question generation, owner command class, expiry and material confirmation reference. This proves only the exact owner command tuple.

Neither fact substitutes for the other. The durable governed command/decision records must retain non-secret references to both authentication results, never either bearer/verifier. Missing/expired/replayed/wrong transport or owner proof makes the ingress proposal-only or rejects it before a governed claim. The adapter cannot set the authenticated flags or principal.

## Call sites to wire

The builder must review exact request/target mappings before edits. Expected integration points are:

- `backend/internal/httpd/owner_commands.go`: extend the existing private loopback S1 minting surface, authenticated by `ownercommand.Authority`, to mint exact `ownerproof` records. The owner bearer stays only in the HTTP authorization header and is never copied into the proof. Material classes require a daemon-validated native confirmation reference.
- `backend/internal/httpd/router.go` and `backend/internal/httpd/api.go`: inject the owner-proof kernel/store into private control dependencies only. The LAN listener remains unable to mount `/internal/owner-commands/**`.
- The accepted S3.3 protected local adapter ingress: authenticate its S3.1 transport binding first, parse content, compute the canonical digest, then call `VerifyAndConsume`; pass only non-secret proof/connection references onward.
- `backend/internal/service/chat/controller.go` `Send` and governed-answer/`Interrupt` paths, plus `backend/internal/service/chat/steer.go` `Steer`: accept a verified authority envelope before creating `GovernedCommand` or `GovernedControlCommand` claims. Existing controller generation, revision, capability and delivery-unknown fences remain unchanged.
- Outcome command boundaries: `service/outcome/attempt.go` `CancelAttempt`, replacement creation currently in `httpd/owner_commands.go`, `service/outcome/plan.go` `ApprovePlan`, and `service/outcome/proof.go` `DecideAcceptance`/`parent_acceptance.go` batch Acceptance. Each material operation must validate its exact confirmation reference and current target/revision before effect.
- Persisted governed command/control and replacement/acceptance records: add non-secret `owner_proof_id` and `harness_connection_id`/generation (or one reviewed normalized authority-reference record) through a new append-only migration and focused sqlc/store changes. Do not overload `OwnerPrincipal`, `CapabilityFingerprint`, request fingerprint or provider correlation fields.

Potential `cancel` ambiguity must be resolved before wiring: chat turn cancel/interrupt and Outcome Attempt cancellation are distinct effects with different target generations. Do not alias one to the other. Likewise `approval` (Plan/authority approval) and `accept` (Result Acceptance) need exact existing domain revision identifiers, not generic target strings.

## Acceptance criteria

1. Paired adapter + exact unconsumed owner proof + matching current tuple creates exactly one governed claim/decision.
2. Valid adapter authentication without owner proof is proposal-only and creates no owner-authorized claim/effect.
3. Valid owner proof without authenticated S3.3 transport cannot enter through adapter ingress.
4. Wrong connection generation/class/binding, wrong proof content/mission/app run/target/generation/class/confirmation, expiry or replay creates no claim/effect and leaks no field-specific secret information.
5. Concurrent duplicate ingress has one durable proof consumer and one governed idempotent result; changed semantics conflict.
6. Crash after proof consumption but before claim persistence cannot redeliver silently. It surfaces a retained action-needed/unknown reconciliation state rather than minting a replacement proof or claiming no effect.
7. Routine current-generation turn/steer/answer/interrupt/cancel does not open a native material confirmation dialog.
8. Replace, Plan/Contract approval or widening, and Result Accept require the exact current native confirmation reference; a routine-class proof cannot authorize them.
9. Existing governed delivery-unknown, quiescence, generation, revision and immutable-claim tests remain green.
10. DB/API/log/argv/env/renderer/repository/plugin scans find no owner bearer, owner-proof bearer/verifier or adapter bearer/verifier. Public records expose only non-secret IDs/fingerprints.
11. Direct loopback without `KennelOwner`, LAN, unpaired adapter and renderer-originated attempts all fail before mint/consume/effect.
12. Restart preserves consumed status and non-secret references, never reconstructs or reissues a bearer.
